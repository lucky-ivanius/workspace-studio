# Foundation

This document describes the setup that is in place and the contracts to work
against. For the brief, see [REQUIREMENTS.md](./REQUIREMENTS.md).

## What runs today

Open the app and you can add a desk, add a chair and accessories, drag anything
to a new tile, turn any item a quarter clockwise where it stands, spin the whole
view clockwise, pan and zoom around the room, and watch the checkout summary
update with live monis.rent prices. That loop exists to prove the foundation,
not to be the final product.

## Stack

| Concern         | Choice                                          |
| --------------- | ----------------------------------------------- |
| Framework       | Next.js 16 (App Router, Turbopack), React 19    |
| Canvas          | pixi.js 8, driven imperatively from a store     |
| State           | zustand 5                                       |
| UI chrome       | Tailwind 4, shadcn (base-luma), lucide icons    |
| Lint and format | Biome                                           |
| Tests           | `node:test` via `tsx`, Playwright for the browser |

Pixi is used directly rather than through `@pixi/react`. The scene needs custom
hit-testing, grid snapping, and depth sorting, which are clearer as imperative
code than as a reconciled tree. React owns every pixel outside the canvas.

## Layout

```
src/features/studio/
  model/        Domain. Pure, no Pixi, no React. Fully unit tested.
    grid.ts       Isometric maths: tile <-> screen, footprints, depth
    types.ts      ArtShape, StudioAttributes, AssetSpec, PlacedItem
    assets.ts     The art contract: PNG sizes derived from a footprint
    art.ts        Which catalog entries the room draws, and what as
    catalog.ts    Typed view over catalog.json
    catalog.json  The database: monis.rent data plus our own `studio` blocks
    art-index.json  The art on disk, by name. Generated by `pnpm art:index`
    placement.ts  Placement rules, surfaces, draw order, rotation
  state/        zustand store and the checkout summary selector
  engine/       Pixi: asset loading and the scene
  components/   React: canvas mount, catalog panel, summary panel, zoom and view controls

e2e/            Playwright browser tests
scripts/
  sync-catalog.mjs                 Seeds catalog.json from monis.rent
  index-art.mjs                    Lists public/assets/studio into art-index.json
  generate-placeholder-assets.mjs  Draws stand-in art at exact sizes
```

The dependency direction is one-way: `components -> state -> model` and
`engine -> model`. Nothing in `model/` imports React or Pixi, which is why it
can be tested with plain Node.

## The grid

The room is a 24x24 isometric grid of 64x32 px tiles. One tile is **20 cm** of
floor, so an 8x4 desk is 160x80 cm — the size monis.rent actually rents, and the
room is 4.8 m square.

Tiles are deliberately smaller than the objects on them. A desk surface is 32
slots, so a monitor (3x1), a lamp (1x1) and a keyboard (2x1) use under a fifth of
it and can be arranged freely while every position still snaps to a grid line.

Tile `(0, 0)` sits at world origin. Moving one tile along `x` goes right and
down; one tile along `y` goes left and down.

```
screen.x = (x - y) * 32
screen.y = (x + y) * 16
```

Items are positioned by the **centre of their footprint**, lifted by their
elevation. Depth is the footprint's front corner, `x + w + y + d`, so larger
means nearer the camera. Two items on the same `x + y` diagonal are the same
distance away and their order is arbitrary.

`gridCorner(x, y)` gives the point where tiles meet rather than a tile centre,
which is what the floor outline and the ruled grid lines are built from.

### The camera

The camera is one world point — the `focus` the view is centred on — plus a zoom.
Both live in the scene, not the store, because they are view state rather than
part of the setup being rented.

Device input, all of which can be mixed freely:

| Gesture | Effect |
| --- | --- |
| Drag empty space | Pan |
| Two-finger scroll, mouse wheel | Pan |
| Trackpad pinch, `ctrl`/`cmd` + wheel | Zoom about the pointer |
| `+` / `-` | Zoom in / out one step (1.25x) |
| `⇧0` | Zoom to 100% |
| `⇧1` | Zoom to fit |

Wheel input is handled with a native listener rather than a Pixi federated one.
Pixi registers its own `wheel` listener as `passive`, so a federated handler
cannot call `preventDefault`, and a pinch would zoom the whole browser page.

A press that travels under 4 px is treated as a click on empty floor and clears
the selection instead of panning.

Zoom runs from 20% to 400%, where 100% is one world pixel per screen pixel.
Zooming holds the world point under the pointer still, which is what makes
pinching feel anchored. The scene reports zoom changes through `onCameraChange`
so the zoom menu can render the current level and disable its limits; pans do not
fire it, because a React render per pointer move would be wasteful.

The focus is clamped to the room's bounds. That means any corner of the floor can
be brought to the middle of the view, and the floor can never be pushed off
screen. A resize re-fits the zoom only while the user has not chosen one of their
own, so a pan or a deliberate zoom always survives a window change.

### The view

The rotate control turns the view one quarter turn **clockwise** — the only
direction it offers, because every drawing has a single facing and two turns
land back where they started. The turns live in the scene beside the zoom.

Every drawing still has a single facing, so a view that would show the room
from its blind side is drawn as its horizontal mirror: on odd turns the whole
world container mirrors (`scale.x` goes negative), which transposes the layout
along with the art. Anything standing on a desk stays standing on it, the
selection tiles and toolbar follow, and drag mapping keeps working — the floor
is symmetric about its centre, so it looks unchanged. Everything that reads
the world's scale treats it as a magnitude (`zoom()`) and divides screen-space
gestures per axis, since x now carries the mirror's sign. Real facings per
view replace the stopgap; the parity rule lives in `model/view.ts`.

### Rotating items

Selecting an item shows a toolbar with a clockwise rotate button and a red
delete button (desks also keep their Add button). The rotate button turns the
item one quarter clockwise where it stands:

- **Footprints transpose on odd turns** — a 2x1 becomes 1x2 — exactly the move
  the mirrored view makes, so the same parity rule composes: the sprite's own
  mirror flag is the item's turn parity, independent of the view's. The turn
  applies in one step, like the view's.
- **The item stays put.** The cell re-anchors so the footprint's centre holds;
  odd-sized footprints round to the nearest tile, so a 2x1 may end up half a
  tile from where it was.
- **A desk carries its riders.** Each item on the surface orbits the desk's
  centre with the turn — the back corner arrives at the right corner — and
  turns with it. The orbit maps the surface exactly onto the surface the
  turned desk offers, so an arrangement that fit before the turn fits after
  it; the desk turn is refused whole if anything would still not fit.
- **A turn that does not fit is refused, not fudged.** `rotated()` in
  `model/placement.ts` builds the room as it would stand after the turn and
  validates every moved item against it — room bounds, host surface, and
  neighbours alike. When any of that fails, `canRotate` is false, the
  toolbar's rotate button disables, and `rotateItem` is a no-op. A 2x1 against
  the wall that can only turn off the room, or off its desk, simply cannot
  turn there.

Everything placement-shaped reads the item's *effective* footprint —
`footprintOf(item)`, the drawing's footprint transposed by its turns — so
dragging, clamping, hit tiles, draw order and desk surfaces all follow the
turn automatically.

### Draw order

`zIndexOf` in `placement.ts` keys draw order on the support hierarchy first and
isometric depth second. An item resting on a desk is keyed off that desk, so it
always draws over it, while a floor item one diagonal nearer still draws over
both. Getting this wrong is subtle, so it is covered by tests.

### Surfaces

An item sits on the `floor`, or on the `desk` surface of a specific host desk.
Desks declare `surfaceHeightCm`; anything placed on one is raised by that
height and constrained to the desk's tiles. Removing a desk clears everything on
it off the canvas, and those items move to the cart rather than off the bill —
see [Losing a surface](#losing-a-surface).

### Where a new item lands

`findPlacement` takes the first free slot, searching **outward from the middle of
the room** rather than in reading order. In a room this size, reading order would
strand the first desk in a back corner. Desk-mounted items search their host
desk in reading order, and chairs try the front edge of a desk first.

## The asset contract

This is the important part. Every PNG has exactly one correct size, derived
from its grid footprint, so art and placement cannot drift apart.

A drawing declares two things about shape, in catalog.json:

- `footprint: { w, d }` — tiles occupied, at 20 cm per tile
- `heightCm` — how tall the real object is

Everything else is computed, by `isoAsset` in `model/assets.ts`:

```
span        = w + d
designWidth  = span * 32
baseHeight   = span * 16           (the footprint rhombus)
standHeight  = round(heightCm * 1.6)
designHeight = baseHeight + standHeight

fileWidth  = designWidth  * 2      (art is authored at 2x)
fileHeight = designHeight * 2

anchor = (designWidth / 2, designHeight - baseHeight / 2)
```

### Drawing an asset

1. Create a canvas at the file size the contract reports — `pnpm
   assets:placeholders --for <slug>` prints it, and leaves a stand-in at exactly
   that size.
2. The footprint rhombus fills the **bottom `baseHeight * 2` px**, edge to edge
   horizontally. That is the floor the object stands on.
3. Draw the object standing on that rhombus, growing upward. It may not exceed
   the canvas top.
4. Leave the rest transparent.

Worked example, `monitor-27-4k` (footprint 3x1, 50 cm tall):

```
span = 4  ->  design 128 x 144  ->  file 256 x 288
footprint rhombus occupies the bottom 128 px of the file
anchor at design (64, 112)
```

The placeholder generator draws this rhombus with a white anchor tick, so you
can open any placeholder to see exactly where the contract puts things.

### Drawing art for a product

Art is found by name: `public/assets/studio/<slug>.png` belongs to the catalog
entry with that slug, and nothing anywhere has to say so.

1. Find the product in `model/catalog.json` and set `studio.placeable` to `true`.
   It is already in the room at this point, drawn as its category's stand-in.
2. `pnpm assets:placeholders --for <slug>` writes a correctly sized stand-in PNG
   named after the slug, and tells you the size.
3. Paint over that file, or replace it with real art at the same dimensions.
4. `pnpm art:index`, which is also run for you by `pnpm dev` and `pnpm build`.

Want a different shape than the stand-in's? Add `footprint`, `heightCm`,
`surface`, and any of `seat`, `flat` or `surfaceHeightCm` to the entry's `studio`
block, then redraw at the new size. `pnpm test` reports the size it expects.

In development, the app also checks every loaded texture against its declared
size and logs a console error naming the file and both sizes if they disagree.

## What the room draws

Not everything monis.rent rents belongs on an isometric floor. Every catalog
entry is either **placeable** or **cart-only**, and `catalog.json` decides which,
in a `studio` block on the entry:

```jsonc
{
  "id": "electrical-adjustable-desk",
  "slug": "electrical-adjustable-desk",
  "studio": {
    "placeable": true,
    "footprint": { "w": 8, "d": 4 },
    "heightCm": 75,
    "surface": "floor",
    "surfaceHeightCm": 75
  },
  "name": "Electrical Adjustable Desk"
  // ... everything else comes from the storefront
}
```

- **Cart-only** — `placeable: false`, or no `studio` block at all, which is the
  default for anything new. Cables, adapters, consumables, and anything held in
  the hand or worn: the smallest thing the grid can hold is a 20 cm tile, and
  none of those would read as more than a speck or a lie about its size. Adding
  one puts it **straight in the cart**: no placement attempt, no question asked.
  It is still rented and still billed, and the catalog card says where it is
  headed with a "Cart only" badge next to the price.
- **Placeable** — `placeable: true`. It can be dropped into the room, dragged
  around, and deleted like anything else.

`model/art.ts` resolves a placeable entry to a drawing in four steps:

1. `studio.art` names a **shared drawing** — one picture for several entries,
   declared once with its own shape under the top-level `studio.drawings`. Six
   27-inch panels look the same on an isometric desk whoever made them.
2. **`public/assets/studio/<slug>.png` exists** — the entry's own art, shaped by
   whatever its `studio` block declares and otherwise by its category's stand-in.
3. Otherwise, the **category's stand-in**: a generic block sized for the kind of
   thing that category holds, named by `studio.generic` on the category. That
   fallback is what lets a hundred-odd products share a handful of drawings, and
   it means a product is in the room the moment it is marked placeable, art or no
   art.
4. A category carrying no stand-in falls back to `studio.fallbackDrawing`, which
   stands on the **floor** rather than on a desk, because a desk stand-in would
   refuse to be added until a desk existed.

So adding art is: drop a PNG named after the slug into `public/assets/studio`,
and flip one flag. There is no mapping table and no code to change. The texture
bundle only loads drawings something actually points at, so art waiting for a
product to claim it costs nothing.

`model/art.ts` runs in the browser and cannot look in a folder, so the file
listing is committed as `model/art-index.json` by `pnpm art:index`. `pnpm dev`
and `pnpm build` regenerate it, and a test fails if the committed copy has
drifted from `public/assets/studio`.

### When the data is wrong

catalog.json is hand-edited, so `artProblems()` in `model/art.ts` is the guard
over it: a shared drawing with no PNG, a category naming a drawing that does not
exist, a footprint in fractional tiles, measurements on an entry that is not
placeable, a desk surface on something that sits on a desk. It returns sentences
rather than booleans, `pnpm test` asserts the list is empty, and the dev build
logs every one of them to the console. A typo in the data is never a silent
blank.

### How an add can end

`store.addProduct` returns one of these, and the UI reads it to decide what to do
next:

| Result | What happened |
| --- | --- |
| `placed` | It is in the room, and selected. The picker closes so you can see it. |
| `carted` | Cart-only, so it went straight to the cart. The picker stays open. |
| `needs-desk` | It sits on a desk and there is no desk yet. Offers the cart. |
| `no-space` | Every surface that could take it is full. Offers the cart. |
| `unknown` | The id names nothing in the catalogue. |

`needs-desk` and `no-space` raise a confirmation over the picker rather than
instead of it: the picker stays open underneath, so answering the question does
not cost the place in the catalogue the choice was made from. The picker closes
only on `placed`, because that is the only outcome with something new to look at.

## Tests

Two layers, each covering what it is good at.

**`pnpm test`** runs `node:test` through `tsx` against `src/**/*.test.ts`. These
are the grid maths, the placement rules, rotation fits, draw order, the store,
and pricing. No browser, no Pixi, so they run in well under a second.

Two are worth calling out. `model/assets.test.ts` reads the IHDR header of every
PNG the room reaches and asserts it matches the size catalog.json implies: draw a
file at the wrong size and `pnpm test` tells you which file and what size it
should be. `model/art.test.ts` asserts `artProblems()` is empty, so a mistake in
a hand-written `studio` block fails the suite with a sentence explaining it.

Browser-level checks (WebGL boot, canvas placement, drags, camera, on-screen
arithmetic) are done ad hoc with the agent-browser CLI driving a real browser
against `pnpm dev`, rather than by a committed e2e suite.

### CI

`.github/workflows/ci.yml` runs on every push to `main` and every pull request:

- **check** — `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`

The Node version comes from `.node-version`, which local tooling (nvm, fnm,
Volta) reads too, so there is one place to change it. The pnpm version comes
from `packageManager` in `package.json`.

A run of the suite against a new commit always rebuilds, so a green tick never
reflects stale output.

## Product data

`model/catalog.json` is the database. monis.rent has no public API, so
`pnpm catalog:sync` pulls the Bali catalogue from their Strapi to **seed** it, and
the file is committed, so nothing fetches at build or request time.

The split is one word:

- Everything **outside** a `studio` block belongs to the storefront — name,
  description, weekly rate, long-stay weekly rate, monthly rate, discount,
  security deposit, source URL. A sync overwrites it. The slug is kept as the id,
  so live data can be joined in later.
- Every `studio` block is **ours**, written by hand, and a sync carries it across
  untouched. So are the top-level `studio` section and the whole `decor` list,
  which the storefront knows nothing about.

A product the API has never shown before arrives with `placeable: false`, so a
sync can never put something in the room that nobody has looked at. The run
prints what arrived, and what it had to drop because the storefront stopped
carrying it.

Items in `decor` (plant, rug) are staging only: they live in catalog.json beside
the rentals and carry the same `studio` block, so adding a prop is the same edit
as making a product placeable. They have no price, never reach the cart, and are
excluded from checkout.

### Pricing

`pricePerWeek` applies to stays under one month; `longStayPricePerWeek` applies
from one month onwards, and is the "From $X/week" figure the storefront shows.
The boundary is four weeks rather than past them, because the storefront's own
`monthlyPrice` is four weeks of the long-stay rate for every product it carries.
`LONG_STAY_WEEKS` holds that number, `weeklyRate` picks the tier and `summarize`
builds the checkout lines. The rental length is chosen from a select at the foot
of the summary, just above the totals it changes.

### Renting more than one

A summary line is one product, however many copies of it are being rented, and
its `[- n +]` stepper is where that number is changed. The two directions are not
symmetrical, because the room is something the user arranged by hand:

- **`+`** adds a **cart copy** only. It is rented and billed, but nothing new is
  drawn, so a step up can never rearrange the canvas. Putting a second one in the
  room is a job for the picker.
- **`-`** gives back a cart copy first, and only reaches for a sprite once the
  cart is empty. The sprite it takes is the **newest** one, by `ordinal`, so
  repeated clicks undo the adds in the order they were made.

So a monitor placed in the room, stepped up once, then added again from the
picker reads 3: two drawn and one carted. Stepping down three times gives back
the carted one, then the second sprite, then the first.

### Losing a surface

Taking a desk out of the room leaves whatever stood on it with nowhere to stand.
Those riders move **to the cart** rather than off the bill, and this is the same
whether the desk went via `-` on its summary line or the trash on the canvas
toolbar. `removeItem` owns the rule, so both paths get it.

The reason is that a line's quantity belongs to that line. Removing a desk is
removing a desk; it may not quietly change what a monitor costs, and a user who
clears the canvas to start the arrangement over has not said anything about
wanting fewer monitors. Each rider is carted individually, so two monitors on the
desk leave two cart copies and the quantity holds.

Staging is the exception, because it is never billed: a prop on a desk has no
cart to fall back to, so it simply goes.

pnpm dev                  # dev server

## Open items

- **Touch pinch.** Trackpad pinch works because the browser reports it as
  `ctrl` + wheel. A two-finger pinch on a touchscreen arrives as touch events
  instead and is not handled yet. Mobile has no catalog panel either, so the
  small-screen experience needs its own pass.
- **A second chair.** The must-haves need two chair options and monis.rent
  currently lists one. `public/assets/studio/chair-task-compact.png` is drawn and
  waiting; rename it after a real chair's slug and it is in the room.
- **Art.** Every drawing is a placeholder block.
- **Deploy.** No hosting is configured yet. CI runs lint, types and both test
  suites, but nothing publishes.
- **Rent action.** The checkout button is inert; it needs to hand off to
  monis.rent's cart.
